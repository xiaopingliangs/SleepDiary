# Safety 与 Real-World Exception Router 架构

`ARCH-FULL-0.1` 工程草案，2026-09-11。当前 SAFETY_RULE_1.0 医学映射与 CBT-I Protocol NONE 不变。下列场景是用户要求的**覆盖目录**，不是已授权的疾病分流规则。关联 [总览](FULL_APP_ARCHITECTURE.md)、[Protocol](CBTI_PROTOCOL_ARCHITECTURE.md)。

## 1. 职责和优先关系

Safety Router 判断已审核的安全约束；Exception Router 处理主协议与现实场景的冲突；Lifestyle/Context 收集用户主动报告的上下文。三者不诊断疾病、不处理药物剂量、不治疗共病。

引擎先检查安全，Exception 给出候选适配后再检查一次。治疗可执行动作集合 = 主协议允许动作 ∩ 当前安全允许动作 ∩ 已审核例外允许动作 ∩ 合法人工指令范围。空集或冲突返回需复核；不能“最后一个规则赢”，不能让多个宽松规则抵消一条安全限制。

`CONTINUE`、`ADAPT`、`HOLD`、`CLINICIAN_REVIEW`、`URGENT_CARE` 是行动能力，不是自创风险等级；`SAFETY_OVERRIDE` 记录覆盖的原因和来源。可同时要求“暂停某动作并联系医生”。具体场景触发哪种行动、暂停哪些任务、何时解除必须有医学审核，不在本文件填映射。

## 2. 持续触发与原始观察

触发工程入口包括：Baseline 提交、治疗激活、review 提交、用户主动报告状态变化、恢复备份后的重新激活、暂停后的恢复，以及规则包更新需复核。是否定期重复哪些医学问题及其有效期尚待批准；不能用“一次回答永久有效”兜底，也不新增每天长问卷。

事件保留 `observedAt`（可未知）、`reportedAtUtc`、自报来源、原答案和被更正关系。用户撤回/更正也留下历史，不把原始安全事实擦掉。旧 S01–S15 的解释与三种 gate 继续按 SAFETY_RULE_1.0 处理；新 Router 用适配器读取，不能将历史 gate 改写成新语义。

自由 comment 不做关键词推断；只有用户明确提交的新评估/情境才成为输入。没填写不是 NONE，技术校验失败不表示无安全问题。

## 3. Exception Rule 结构

| 字段 | 语义 |
|---|---|
| exception_rule_id / ruleVersion / rulesetVersion | 不可变规则身份 |
| sceneCodes / inputSchemaVersion | 支持的结构化场景与回答版本 |
| sourceRefs / sourceSection / reviewStatus | 依据和逐条临床审核，缺失则不可执行 |
| requiredFacts / applicability / exclusions | 必需事实、适用条件、排除条件；不能从疾病名称单独推断 |
| constraints / candidateActions | 可受限的具体动作或已审核解释，不执行任意自由文本 |
| priorityClass / safetyDependencies | 依赖安全约束；不通过数值优先级自创严重度 |
| scope / validity / reassessment | 一次/某计划/某阶段范围，持续与终止规则待审核 |
| knowledgeRefs / clinicianQuestions | 统一解释和需要向医生核验的问题 |
| conflictPolicy / testCaseRefs | 与主协议及其他规则冲突时的已审核解决方式与判例 |

ExceptionDecision 保存原事件、输入快照、所有命中规则、约束合并结果、原因、适用时限和原计划引用。若仅某动作需暂停，不能自动扩展为停止所有活动；反之也不能在没依据时默认其他治疗都安全继续。

## 4. 场景覆盖矩阵（全部待规则审核）

| 场景组 | 必须覆盖的用户情境 | 架构需保留的区分；不在此决定处理 |
|---|---|---|
| 身体状态 | 头晕、身体不适、发热/生病、疼痛、跌倒风险 | 发生时点、当前活动、用户描述和已知临床意见 |
| 日间清醒 | 明显 sleepiness、不由自主睡着、疲劳 | 疲乏与入睡倾向不同；新旧变化及危险活动关联 |
| 危险活动 | 驾驶、机械、电气、高处工作 | 所在场景与安全受影响；不为维持睡眠驱动力鼓励硬撑 |
| 安全例外 | safety nap | 专用审核规则；时间、时长、适用条件、复核/终止均留空待批准 |
| 作息冲突 | 旅行、时差、倒班、临时加班 | 既定计划与当前时区/工作要求，不能默认平移旧窗口 |
| 药物 | 调整、漏服、停药、用户报告的变化 | 记录并提供临床沟通路径；不建议补服、停药或改变剂量 |
| 特殊人群/状态 | 怀孕/产后、严重身体疾病、癫痫、双相/躁狂提示、急性精神问题、自伤/自杀信号、OSA、物质使用、PTSD 暴露治疗 | 对应 Safety 覆盖候选；不是把这些情况一律禁用 CBT-I，更不是自诊 |
| 个人活动 | 性活动、自慰 | 个体影响与时间/场所；不按男女性别给统一结果 |
| 屏幕/娱乐 | 手机、短视频、电子游戏、看剧、听书/音频 | 唤醒程度、延迟、能否停止、是否在床上、依赖性，不一刀切 |
| 生活环境 | 咖啡因、酒精、运动、临时压力、环境变化 | 自报活动与影响；不引入当前 Diary 的结构化每日必填字段 |

上述目录保证后续研究不遗漏用户场景；任何一行都不隐含它已被主手册或指南逐项讨论。来源不足的场景标记 UNSUPPORTED，不虚构引用。

## 5. Fatigue / Sleepiness 与安全例外

教育按用户要求区分：fatigue 是疲乏/没力气/想休息，sleepiness 是实际入睡倾向、维持清醒困难甚至不由自主睡着。用体验区分，不通过“为什么产生”定义。

数据分别记录治疗前长期存在、SRT 开始后新出现、药物变化后出现、时间关系不清楚；这些是时间关联，不能输出因果诊断。具体强度阈值和动作映射待审核，不能本轮自造“几分就暂停”。

safety nap 是有限安全例外候选，不是每天推送的补觉任务。确切规则来自主协议或经正式审查可兼容的补充安全资料；若需要扩充医学规则必须显式批准。规则未齐不能给出时长/时点，也不能改写普通 SC 规则。未知例外不交由外部 AI 来决定是否能继续危险活动。

## 6. 不支持、相互矛盾与人工介入

- 无匹配规则：明确“此情境没有已审核的自动处理规则”，可展示已有通用知识、记录待问医生的问题；不自动生成个体治疗适配。
- 关键输入缺失：列出最少必要的获批问题；未答可退出，日记可用，但不把缺项当安全许可。
- 规则冲突：记录全部命中及冲突；不出新的相互矛盾指令。既有计划能否继续必须由有效安全规则确定，否则技术上抑制相关治疗输出并请求复核。
- 已审核急性帮助触发：优先静态、可离线访问的帮助内容和当地渠道；实际触发、地区号码、措辞需医学/本地化审核。不能等待 AI 或知识库在线检索后才处理。
- 医生意见：按 [Clinician Bridge](CLINICIAN_BRIDGE_ARCHITECTURE.md) 核验来源、范围与有效性；不会因用户粘贴一段文字而消除 Safety 限制。

## 7. 测试与完成条件

以“场景 × 前后状态 × 关键缺项 × 多规则冲突 × 数据时间 × 输出范围”建立审查矩阵。工程属性测试验证：更严格约束不会被宽松适配解除；新事件使过期 proposal 失效；重启/恢复不清除 hold；从设置返回保留已持久化 DRAFT；同输入同规则可重放。

每条医学映射另需临床金标准、来源定位、中文解释审核及紧急帮助可达性测试。只有目录覆盖、按钮可点或枚举测试通过，不算 Exception 模块临床完成。
